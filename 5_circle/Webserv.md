
## Introduction

하이퍼텍스트 전송 프로토콜(HTTP)은 분산형, 협업형, 하이퍼미디어 정보 시스템을 위한 애플리케이션 프로토콜입니다. HTTP는 월드 와이드 웹에서 데이터 통신의 기반이 되며, 하이퍼텍스트 문서는 다른 자원에 대한 하이퍼링크를 포함하고 있어 사용자가 웹 브라우저에서 마우스 클릭이나 화면 터치만으로 쉽게 접근할 수 있습니다.

HTTP는 하이퍼텍스트 기능과 월드 와이드 웹의 성장을 지원하기 위해 개발되었습니다.

웹 서버의 주요 기능은 웹 페이지를 저장, 처리, 그리고 클라이언트에게 전달하는 것입니다. 클라이언트-서버 간의 통신은 하이퍼텍스트 전송 프로토콜(HTTP)을 통해 이루어집니다. 전달되는 페이지는 대부분 HTML 문서이며, 여기에 텍스트 콘텐츠뿐만 아니라 이미지, 스타일 시트, 스크립트 등이 포함될 수 있습니다.

트래픽이 많은 웹사이트의 경우 여러 대의 웹 서버를 사용할 수 있습니다.

사용자 에이전트(일반적으로 웹 브라우저나 웹 크롤러)는 HTTP를 사용해 특정 자원을 요청함으로써 통신을 시작하고, 서버는 해당 자원의 콘텐츠나, 불가능할 경우 오류 메시지로 응답합니다. 이 자원은 보통 서버의 2차 저장장치에 있는 실제 파일이지만, 웹 서버 구현 방식에 따라 반드시 그렇지는 않습니다.

HTTP는 주로 콘텐츠를 제공하는 기능을 하지만, 클라이언트가 데이터를 전송하는 것도 가능하게 합니다. 이 기능은 웹 폼 제출, 파일 업로드 등에 사용됩니다.


## General rules

- 프로그램은 어떠한 상황에서도(메모리가 부족한 경우 포함) 크래시나 예기치 않은 종료가 발생해서는 안 됩니다.  
    이 경우 프로젝트는 비정상 작동으로 간주되어 0점 처리됩니다.
    
- 소스 파일을 컴파일하는 Makefile을 제출해야 하며, 불필요한 재링킹을 수행하지 않아야 합니다.
    
- Makefile에는 최소한 $(NAME), all, clean, fclean, re 규칙이 포함되어야 합니다.
    
- 코드는 c++ 컴파일러로 -Wall -Wextra -Werror 플래그와 함께 컴파일되어야 합니다.
    
- 코드는 C++ 98 표준을 준수해야 하며 -std=c++98 플래그 추가 시에도 컴파일이 가능해야 합니다.
    
- 가능한 한 많은 C++ 기능을 활용해야 합니다(예: <string.h> 대신 \<cstring> 사용). C 함수 사용은 허용되지만 C++ 버전이 존재할 경우 항상 우선적으로 선택해야 합니다.
    
- 외부 라이브러리와 Boost 라이브러리는 사용이 금지됩니다.

### Requirements

- 프로그램은 구성 파일을 인자로 받거나 기본 경로를 사용해야 합니다.

- 다른 웹 서버를 execve로 실행해서는 안 됩니다.
    
- 서버는 항상 비차단(non-blocking) 상태를 유지해야 하며 필요할 때 클라이언트 연결 종료를 적절히 처리해야 합니다.
    
- 비차단 방식으로 동작해야 하며 서버와 클라이언트 간의 모든 I/O 작업(리스닝 포함)에 대해 1개의 poll()(또는 동등한 함수)만 사용해야 합니다.
    
- poll()(또는 동등한 함수)는 읽기와 쓰기 작업을 동시에 모니터링해야 합니다.
    
- poll()(또는 동등한 함수)를 거치지 않고 read/write 작업을 수행해서는 안 됩니다.
    
- read/write 작업 후 errno 값을 확인하는 것은 엄격히 금지됩니다.
    
- 구성 파일을 읽기 전에 poll()(또는 동등한 함수)를 사용할 필요는 없습니다.


<span style="background:#ff4d4f"> WARN </span>
> 비차단(non-blocking) 파일 디스크립터를 사용해야 하므로, poll() (또는 이와 동등한 함수) 없이 read/recv나 write/send 함수를 사용하는 것만으로도 서버가 블로킹되지 않을 수 있습니다.  
> 하지만 이렇게 하면 더 많은 시스템 자원을 소모하게 됩니다.  
> 따라서 poll() (또는 이와 동등한 함수) 없이 어떤 파일 디스크립터에 대해 read/recv나 write/send를 시도할 경우, 점수는 0점이 됩니다.

- FD_SET, FD_CLR, FD_ISSET, FD_ZERO와 같은 모든 매크로 및 정의를 사용할 수 있습니다(이들이 무엇을 하는지, 어떻게 작동하는지 이해하는 것이 매우 유용합니다).

- 서버에 대한 요청이 무한정 멈추어서는 안 됩니다.
    
- 서버는 선택한 표준 웹 브라우저와 호환되어야 합니다.
    
- NGINX가 HTTP 1.1을 준수한다고 간주하며 헤더와 응답 동작을 비교하는 데 사용될 수 있습니다.
    
- HTTP 응답 상태 코드는 정확해야 합니다.
    
- 제공된 페이지가 없을 경우 기본 오류 페이지를 갖추어야 합니다.
    
- CGI(예: PHP, Python 등) 이외의 목적으로 fork를 사용할 수 없습니다.
    
- 완전한 정적 웹사이트를 제공할 수 있어야 합니다.
    
- 클라이언트가 파일을 업로드할 수 있어야 합니다.
    
- 최소한 GET, POST, DELETE 메서드를 지원해야 합니다.

- 서버가 항상 가용하도록 스트레스 테스트를 수행하세요.

- 서버는 여러 포트를 수신할 수 있어야 합니다(설정 파일 참조).


### Configuration file

<span style="background:#fff88f"> HINT </span>
> NGINX 설정 파일의 'server' 섹션에서 영감을 얻을 수 있습니다.



구성 파일에서 다음을 할 수 있어야 합니다:

- 각 '서버'의 포트와 호스트를 선택할 수 있습니다.
    
- server_names를 설정하거나 설정하지 않을 수 있습니다.
    
- 하나의 host:port에 대해 첫 번째 서버가 해당 host:port의 기본 서버가 됩니다(즉, 다른 서버에 속하지 않는 모든 요청에 응답합니다).
    
- 기본 오류 페이지를 설정할 수 있습니다.
    
- 클라이언트 요청 본문의 최대 허용 크기를 설정할 수 있습니다.
    
- 다음과 같은 규칙/구성을 하나 이상 가진 라우트를 설정할 수 있습니다(라우트는 정규표현식을 사용하지 않습니다):
    
    - 라우트에 대해 허용되는 HTTP 메서드 목록을 정의할 수 있습니다.
        
    - HTTP 리다이렉트를 정의할 수 있습니다.
        
    - 요청된 파일이 위치할 디렉터리 또는 파일을 정의할 수 있습니다(예: url /kapouet이 /tmp/www에 루팅되어 있다면, url /kapouet/pouic/toto/pouet은 /tmp/www/pouic/toto/pouet이 됩니다).
        
    - 디렉터리 목록 표시를 활성화하거나 비활성화할 수 있습니다.


	- 요청이 디렉토리인 경우 제공할 기본 파일 설정 (예: index.html)  
	- 특정 파일 확장자(예: .php) 기반 CGI 실행  
	- POST 및 GET 메소드 처리 기능 구현  
	- 파일 업로드 허용 및 저장 위치 구성  
		∗ CGI(Common Gateway Interface)란 웹 서버와 외부 프로그램 간의 데이터 교환 인터페이스입니다.  
		∗ CGI를 직접 호출하지 않고 전체 경로를 PATH_INFO로 사용해야 합니다.  
		∗ 청크 요청의 경우 서버에서 청크를 해제해야 하며, CGI는 본문 끝을 EOF로 인식합니다.  
		∗ CGI 출력에도 동일하게 적용: content_length가 반환되지 않으면 EOF로 데이터 종료를 판단합니다.  
		∗ CGI 호출 시 첫 번째 인자로 요청된 파일을 전달해야 합니다.  
		∗ CGI는 상대 경로 파일 접근을 위해 올바른 디렉토리에서 실행되어야 합니다.  
		∗ 최소 한 가지 CGI(php-CGI, Python 등) 지원 필요

평가 시 모든 기능 검증을 위한 구성 파일 및 테스트용 기본 파일 제공이 필수적입니다.
